# 阶段探索、双层 Memory 与受约束的程序自改进

状态：阶段、子任务级 code 接管、Grounding/RGB-D、双层 Memory、Flora 理由和 OS 隔离已实现。
调度策略已支持有界候选；自动评测晋级/回滚尚未实现。实际接口与验证见 [框架更新](framework-v2.md)。
以 CloseToasterOvenDoor 为首个开发任务，使用同一 OmniSF/pi05 权重，验证监督与恢复带来的收益。

## 原子任务也拆阶段

Benchmark 的 atomic 标签不规定内部控制粒度。Astra 可以拆分、合并和修订执行阶段；
阶段用于观察、局部恢复与经验归因，不要求每次阶段变化都暂停 VLA 或改写其语言指令。
当前“只有 task_success 就只能一个可执行子任务”的约束需要与阶段规划解耦。

以下是关烤箱门的初始阶段模板，Astra 应根据实际场景修订，而非固定每条轨迹必须完整经过：

| 阶段 | 需要的证据 | 可探索的局部程序 |
|---|---|---|
| 定位与接近 | 门板/把手候选区域、可用视角、末端相对位置 | 重新观测、重定位、调整接近路径 |
| 对齐与建立接触 | 末端与门的几何关系、动作后门是否响应；无直接接触证据时保留 unknown | 调整接触点、末端姿态、接近方向 |
| 推进闭合 | 门的可见运动趋势、目标偏差、阻塞或脱离现象 | 分段闭合、重新对齐、调整路径和执行速度 |
| 完成核验 | 当前视觉证据与固定的任务成功判据 | 补充观察；未完成时回到有证据支持的阶段 |

每个阶段记录目标、前置条件、当前执行器、输入证据引用、成功/失败观察条件、
原因假设、时间与尝试预算、代码版本、交还条件及证据强度。
阶段状态可以是 inferred、assessed、verified 或 unknown，不能把模型判断伪装成传感器事实。
阶段估计更新不等于动作控制权转移，也不要求末端执行器速度在边界变为零。

## Code Policy 的责任范围与交还边界

更新原则：Astra 指定一个有明确终态和完成条件的子任务后，Code Policy 负责从当前状态完成
该子任务的剩余工作。内部仍细拆定位、接近、接触、推进等步骤，以便诊断与修改；
单个内部步骤成功、重新对齐成功或程序返回 RECOVERED，不自动触发交还 VLA。

任务、子任务和程序步骤需要分别表示。子任务是执行器承担的目标，步骤是程序内部组织和检查单位。
边界由 Astra 根据任务依赖、可观测终态与接续条件确定，不仅由 benchmark 的 atomic/composite 标签决定。
例如 Code Policy 若接管 CloseToasterOvenDoor 的关门目标，应继续做到关门通过核验；
该目标若已是 Episode 最后任务，则直接结束，无需重新启动 VLA。

同一子任务的代码版本失败后，可暂停动作、由 Astra 读取反馈并修订，再继续代码尝试。
修订期间物理控制权可以由宿主持有，但逻辑上的子任务执行器分配仍为 code，VLA 保持暂停。
新版本重新读取实际状态、检查前置条件，不盲目重做已完成步骤，也不按旧步骤编号直接跳过动作。
预算耗尽或能力不足时交 Astra 重规划或停止，不自动让 VLA 重试同一个未完成子任务。
子任务通过固定核验后，Astra 才为后续子任务选择 VLA 或 Code Policy；不默认一定切回 VLA。

实现上需要将子任务执行器分配、程序运行结果与物理动作 lease 分离，并绑定子任务/目标版本。
`code_session.py` 已实现上述分离。CloseToaster 开发配置改为 150 步/次，所有代码动作计入 450 步 Episode 总预算。

参考 RAX 的 robodojo-behavior/native 版本：编码 Agent 从成功探索中提取可复用函数，
有监督控制模式要求每个步骤检查可观测前置条件与完成条件，返回结果、测量和失败原因；
main(ctx) 串联步骤，在失败处返回。监督 Agent 可以修订、恢复后从满足前置条件的步骤继续。
冻结控制器模式则将完整程序登记后独立运行。这是程序组织方式，并非统一的 VLA/Code 交还规范。
源文件：[autonomous-control](https://github.com/robot-agent-exploration/rax/blob/16e75db0d0258a4870935d0c4b2402ab618db11d/agent_skills/auto-research/autonomous-control/SKILL.md)。

Flora/Astra 可提供阶段质量与完成的判断证据。Outcome 是终局评分，
不能直接把未完成阶段的低分判为失败；阶段提示词、Dense/Rubric 的在线适用性需单独验证。
所有在线判断只使用当前时刻以前的信息。最终任务 SR 仍使用固定的原生成功判据。

## Grounding 与 RGB-D 支持程序探索

参考本地 RAX 的观测绑定、像素到三维点、几何质量检查和动作后重新定位流程。
以下描述目标能力；已实现的 bbox 选择和局部几何接口及其限制见 [框架更新](framework-v2.md)：

1. `ground_target(goal, observation_id, camera)`：输出目标区域、关键点或 mask，包含
   原图坐标、观测步数、来源及不确定性。第一版可由 Astra 选择视觉区域，再逐步接专门定位模型。
   选中目标区域尚不等于找到可执行接触点。
2. `query_geometry(grounding_id)`：使用对齐的米制深度、相机内参和该时刻外参，
   提取局部可见点云、表面位置/方向和末端相对关系，并返回坐标系、有效深度比例及误差指标。
3. Astra 将几何证据和阶段失败现象转成可验证的恢复假设，写入版本化程序。
4. 程序通过 Harness 短段执行，在重要接触与移动后重新观测、定位和计算。
   再根据实际对象运动、Flora 判断和阶段证据修改相关代码或参数。
5. 保存前后观测、实测轨迹、程序版本、原因假设及验证结果；在不同布局重复检查后形成技能。

像素反投影和坐标变换由工具数值计算，语言模型接收必要几何摘要、质量标记和图像。
原始深度、点云和完整动作日志保留为工具可读数据，不全部展开进语言上下文。

RoboCasa 接入首先需要验证 RGB/深度的翻转与缩放、米制深度含义、内参和外参，
并把输出转换到控制器实际使用的基座坐标系。运动相机使用观测时刻的位姿。
通过可见机器人点的重投影、多视角同特征一致性和相机运动后的重复定位检查，验证几何链路。
RAX 的 Isaac 相机内参修正是后端特有处理，不能照搬到 MuJoCo。

深度缺失、反光/透明表面、遮挡或匹配不一致时，结果应为不可靠，随后重新观察或调整视角。
可见表面点不等于物体中心、铰链轴、可抓取姿态或无碰撞路径；铰链方向等未观测参数需要额外证据。
仿真器的物体真值不作为在线 Grounding/几何工具的替代；离线调试若使用，应单独标记并隔离。

当前已接 bbox Grounding 与对齐的几何计算；专门定位模型、跨视角匹配、接触精度和路径规划仍待完善。

## 短期与长期 Memory

| 范围 | 内容 | 用法 |
|---|---|---|
| 短期：当前 Episode/尝试 | 阶段图与版本、有效指令、观测锚点、目标定位、最近进展、Flora 判断、失败假设、已试代码和剩余预算 | Astra 判断当前缺什么证据、继续哪个执行器、下一次修改验证什么 |
| 长期：跨 Episode | 任务阶段模板、失败模式、适用条件、工具调用经验、版本化技能、成功/失败证据、代价及失效条件 | 为当前阶段检索候选策略与工具，减少重复探索 |

长期 Memory 不只是 task_name 到 tool_name 的映射。同一任务可能因门型、视角、控制器、
失败阶段和传感器可用性不同而需要不同工具；也要记住何时 VLA 可以自行完成、何时介入反而有害。
长期条目应以任务/阶段/机器人/可观测条件检索，返回适用条件、证据引用、版本和已知失败。
当前场景重新计算几何参数，不把某次成功的绝对坐标当作通用技能。

Episode 结束后自动写入候选经验，成功与失败都保留；验证后再成为默认可复用经验。
长期条目失效、模型/控制器改变或结果退化时，降级或回退。原始日志独立保存，摘要保留证据索引。
Memory 提供建议和历史证据；当前工具权限、硬预算和最终成功判据仍由宿主维护。

## Astra 可修改的范围

第一版目标是固定模型权重下的程序和调度策略自改进。能力是否提高由独立评测确认，
修改更多代码或获得更高的自评 reward 不能单独算作 RSI 成功。

| 部分 | Astra 权限与生效方式 |
|---|---|
| 阶段恢复程序、技能参数、目标选择策略 | 在候选工作区创建新版本；可在同一恢复会话内经宿主检查、重新观测后试运行 |
| Decision 的输入选择、提示词、检查频率、阈值与复核策略 | 提出有界候选版本；开发评测通过后在下一 Episode 生效 |
| Flora 的调用时机、窗口、模式、阶段 rubric 与提示词 | 提出候选并测试；用于晋级和最终评测的成功定义不由这些修改决定 |
| 经验归纳、检索排序、工具选择策略 | 版本化并验证；不能凭文本直接获得额外工具权限或把候选标为 verified |
| Harness 唯一控制权、停止与动作校验、版本/时效检查、坐标协议 | 固定核心，不允许自修改 |
| 真实回执、原始日志、模型输出合法性检查和硬预算上限 | 固定核心，不允许覆盖、删改或放宽 |
| 原生成功判据、验收数据划分、评测计分、版本晋级与回滚机制 | 独立固定流程，候选代码不能修改自己的验收规则 |
| 模型权重、环境/控制器、进程权限与工具权限表 | 第一版固定；不属于自主修改面 |

可修改策略通过窄接口返回建议，由固定宿主验证和执行。不能把可编辑插件直接作为
拥有完整宿主权限的 Python 模块加载。受保护源码、日志和评测数据应从操作系统权限/挂载层隔离，
策略进程只能写候选工作区，通过有权限和预算检查的接口访问工具。
路径白名单、提示词承诺、语法检查和文件哈希本身不能构成完整隔离。
当前默认 worker 已启用 Landlock + seccomp；声明式调度候选不能加载任意宿主 Python。自动晋级仍未开放。

## 两个改进闭环

在线子任务循环：定位问题阶段 → 检索/修改 Code Policy → 新观测下执行 → 记录效果 → 再修订，
直到完整子任务通过核验，或预算耗尽后返回 Astra。内部阶段完成不触发 VLA 接管。
它允许改程序版本，不允许运行中的程序随时改写自己的动作执行核心。

跨 Episode 循环：归纳案例 → Astra 提出单项可解释修改 → 固定测试器检查契约 →
开发场景和回归场景配对比较 → 达标后自动登记并切换版本 → 监测退化并回滚。
频繁调参使用开发/回归集合；最终验收使用未参与选择的场景，避免把不断试验的验证集当成全新测试集。

验收首先看同预算下原生任务 SR、救回失败数及破坏原成功数，再比较耗时、调用次数和成本。
Flora 分数用于诊断，不替代真实成功率。代码恢复步数计入相同预算；探索成本与冻结技能执行成本分开报告。
第一轮先完善阶段跟踪、RGB-D/Grounding、Flora 证据与代码技能改进；稳定后再开放调度策略自改进。
